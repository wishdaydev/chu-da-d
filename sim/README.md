# sim —— 大师模式仿真与性能基准

纯 JVM 跑的离线工具，不依赖 Android SDK / Gradle。业务代码与 App 同源（直接编译 `app/src/main/java` 下的
`model/`、`CardRuleEngine`、`AIDecision`、`MasterSearch`、`PerfBench`），所以结论可以代表线上行为。

```
sim/
├── run-sim.sh   编译 + 运行（仿真 / 性能基准两种模式）
├── SimMain.kt   4 人对局仿真：胜率、回合数、非法走法、每步搜索量
├── PerfMain.kt  性能基准：与 App 内「设置 → 性能测试」同一份实现
└── README.md
```

## 一、快速开始

```bash
# 固定 12 万节点预算跑 100 局（推荐：A/B 对比用这个）
SIM_NODES=120000 ./sim/run-sim.sh 100 0 0 4 7

# 时间预算：每步 300ms
./sim/run-sim.sh 100 300 500000 4 7

# 性能基准：与手机端同一份代码、同一批局面
./sim/run-sim.sh perf 300
```

参数依次为 `games deadlineMs nodeLimit threads baseSeed`。

## 二、两种预算模式：为什么推荐固定节点

| | 时间预算 | 固定节点预算（`SIM_NODES`） |
|---|---|---|
| 停止条件 | `deadlineMs` 到点 | 节点数到上限 |
| 可复现性 | 同一 seed 两次跑可能不同决策 | **完全确定**，逐字节相同 |
| 受 CPU/负载影响 | 是（并行跑多组会互相拖慢、深度变浅） | **否**（超订只拖时长，不改结果） |
| 每步耗时 | 恒定 | 随局型浮动 1.6 倍 |
| 贴近真机 | 是（真机就是时间受限） | 否（会把开局搜得比真机更深） |

实测（30 个局面，JIT 预热后）：同样 300ms，**开局只能搜约 9.6 万节点、中局能搜约 16 万节点**
（走法生成成本不同），节点数 p5~p95 从 8.4 万到 19 万。也就是说时间预算买到的是**不等量的思考量**，
不同配置的牌局若落在不同局型分布上，深度差异会混进结论。

所以：
- **A/B 对比、调参 → 固定节点**（消除噪声，差异只剩策略本身）；
- **对齐真机表现 → 时间预算**（跑小样本交叉验证，确认固定节点得到的结论方向没变）。

> 注意：沙箱 cgroup 只给 4 核。若并行跑多组，时间预算下会超订、每组实际深度不同，结果不可比。
> 固定节点无此问题，但仍建议 `threads` 不超过核数。

## 三、环境变量

| 变量 | 默认 | 含义 |
|---|---|---|
| `SIM_NODES` | 无 | 设了就走固定节点预算（自动把 deadline 放宽到 600s） |
| `HEURISTIC_SEATS` | 空 | 哪些座位用普通模式 `AIDecision` 出牌，如 `0` 或 `0,2`；其余用大师搜索 |
| `HUMAN_MODEL_SEAT` | -1 | 把哪个座位当「人类」建模（-1 = 不建模，四家全大师） |
| `HUMAN_MODEL_WEIGHT` | 0.0 | 建模强度：1 = 完全信任代理走法，0~1 = 软建模，0 = 全量展开对照 |
| `SELFISH_SEATS` | 全部 | 哪些座位用 selfish 对手模型（线上默认全部；设空集即退回 paranoid） |
| `OPP_TOPK` | 2 | selfish 模型每个对手节点保留的候选数 |
| `MAX_DEPTH` | 64 | 迭代加深上限（压到 8~12 可做「浅搜索」对照） |
| `JAVA_OPTS` | `-Xss32m -Xmx4g` | JVM 参数；容器里务必保留堆上限，否则默认 1/4 物理内存会被 cgroup OOM kill |

常用组合：

```bash
# 全大师基线（四家都大师）
HUMAN_MODEL_SEAT=-1 ./sim/run-sim.sh 100 ...
# 3 大师 vs 1 个普通模式代理，不开建模（= 测大师对外强度）
HEURISTIC_SEATS=0 HUMAN_MODEL_SEAT=0 HUMAN_MODEL_WEIGHT=0 ./sim/run-sim.sh 100 ...
# 线上配置：其余 3 座对 0 号座按 w=0.8 软建模
HEURISTIC_SEATS=0 HUMAN_MODEL_SEAT=0 HUMAN_MODEL_WEIGHT=0.8 ./sim/run-sim.sh 100 ...
```

## 四、性能基准与手机对齐

`./sim/run-sim.sh perf <budgetMs>` 与 App「设置 → 性能测试」跑的是**同一个 `PerfBench`**：
标准 52 张开局，把持 ♦3 的手牌换到 0 号位（口径固定为「0 号先出、首手含 ♦3」），
不建人类模型，对手模型取线上默认；预热 2 组丢弃后跑 10 组，记录每组的节点数 / 完整深度 / 耗时。

沙箱参考值（JVM 20，4 核配额，300ms，10 组，2026-10 实测）：

```
平均节点 96127（中位 102573，范围 47142~145468）
平均深度 24.5 层
搜索速率 320 节点/ms（每万节点 ≈ 31.2ms）
```

两点解读上的注意：

- **组间离散度大（约 3 倍）是正常的**：不同开局的走法生成成本差很多（能出同花/顺局的分支多）。
  所以看**中位数**比看均值可靠；手机与沙箱逐行比对时，因为用的是同一批 seed、同一批局面，
  节点数完全相同，只有耗时不同，比值仍然成立。
- **不要跨预算档比速率**：`节点/ms` 不是纯算力常数。每次决策有固定开销（根走法枚举、排序、
  State 构造）不计入节点数，预算越短这部分占比越高（实测 100ms 档 168 节点/ms，300ms 档 320）。
  **对齐机型请用同一档预算**（建议都是 300ms）。

手机端跑同样一组后：

```
手机算力比 = 手机速率 ÷ 沙箱速率（同为 300ms 档）
等价节点预算 = 手机预算(ms) × 手机速率(节点/ms)
```

即「手机 5 秒能搜多少节点」，然后用 `SIM_NODES=<该值>` 跑仿真，结论才与真机同档。

## 五、结果怎么读

```
=== 结果 ===
玩家0 胜率: 12/50 (24.0% ±12.0)      ← ±X 是 95% 置信区间
平均回合数: 61.2  (完成局数 50/50, 异常 0)
搜索量: 平均每步 118000 节点 / 24.3 层（最深 33 层，步数 3050，预算 固定节点 120000节点）
非法走法次数: 0
总耗时: 212000ms  (worker=4)
```

- **公平值 25%**：四家牌力均等，某个座位显著偏离 25% 说明该配置有系统性优势/劣势。
  注意 100 局的 95% 置信区间约 ±8.5pp，**单 seed 100 局分不出 5pp 以内的差异**，
  要坐实到 ±4pp 需 400 局，并建议换 seed 复跑确认方向一致。
- **非法走法必须为 0**：非 0 说明搜索输出了不合规则的牌，脚本会用最小合法走法继续推进并打印样本。
- **搜索量**：固定节点模式下 `平均每步` 会略低于上限（部分局面提前算出必胜/必败而结束）；
  时间预算模式下它反映「这个档位实际花了多少预算」，可用来核对是否与预期档位一致。
